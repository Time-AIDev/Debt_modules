# Feedback release: 5 October 2026

Source: [Debt feedback](https://docs.google.com/document/d/1G2yidETrYI2PccL8FpguKzxIiMXg7-CQ8uNgRecXpfA/edit).

The release counts automatically matched invoices from their collection due date in Asia/Bangkok. Historic schedule confirmations remain available as evidence, but the overview no longer asks officers to confirm a schedule before matching. Imported documents match by contract and service/due month; ambiguous records remain visible with a reason. Invoice and cycle counts are separate.

Case balances, payment positions and customer invoice previews use a common invoice projection. A due date is included that day and becomes overdue the next day. Deferrals retain the PEAK date and move collection calculations to the adjusted date. Future calendar cycles remain visible; future and whole-contract balances are served separately.

Invoice review is retrospective certification, not a payment. Rejecting a document removes its collection liability while retaining the source invoice and receipts. Accept can restore it after correction. Durable decisions use company plus source document identity, survive reimport/restart, and require a new certification when material source data changes. The rightmost column and bulk drawer share one preview/commit API. Bulk covers every eligible due invoice for the current customer, independently of table pagination; rejection needs a reason and every commit needs a final acknowledgement.

## Additive migration

Run `python -m app.migrate` from the release API image with the existing migration role/configuration. `backend/app/schema.sql` adds `records.invoice_review(sequence, uid, payload)` and its append-only UPDATE/DELETE guard. Existing runtime grants include the new table and sequence. Each event stores all decisions, the idempotency fingerprint, actor, reason, source fingerprints and before/after balances in one transaction. Local fixture environments use a SQLite store. Import snapshots and receipts are not rewritten by review.

## Validation

The suites cover calendar matching without confirmation, due-day boundaries, multiple invoices per cycle, duplicate company/document identities, ambiguous records, receipt preservation, reject/restore, changed source data, restart/reimport, stale preview, replay/conflict, bulk rollback and all allowed roles/assignment boundaries. Row deferral uses the existing validation for paid, partially paid and pending-payment cycles.

Frontend tests cover the complete bulk list, required rejection reason, final checkbox, stale preview, row preselection, disabled reasons and tooltip focus/tap/Escape. Browser checks use an isolated synthetic customer with 48 future/calendar cycles and 26 currently due invoices; no production customer is altered. Both Thai and English are checked, including a 390px viewport.

Exact suite results and deployed image/revision identities are captured in the release evidence at rollout time.

## Rollout and rollback

- GCP staging: project `dept-collection-508109`, region `asia-southeast1`, service `volt-debt-uat`. Build the release, migrate using the existing `debt-migrate` job, deploy a tagged revision with no traffic while preserving service configuration. Verify readiness, authentication and all five features through the candidate URL before promoting traffic. Previous traffic remains available for rollback.
- SSH production: `debt-production`, `/srv/volt-debt-platform`. Archive the canonical release into `/srv/volt-debt-releases/<SHA>` and build API/web images with the same release SHA. Retain the existing Compose/Caddy, `collection.volt.co.th`, backup/health timers and private configuration. Before updating images, run the existing backup to capture DB/config/private objects and record old image IDs. Test the candidate image against a disposable isolated database, run the additive migration, then update API/worker/web and verify readiness, authentication and queue health.
- Preserve `PROD_GO_LIVE_ENABLED=false`. This release updates the existing deployment; public go-live and a new GCP production stack are outside its scope.
- On failed checks, restore staging traffic or the old SSH API/web image references. Keep the new review/audit tables. If collection balances are wrong, stop writes until the restored version is verified. Never downgrade customer data or replace GitHub history with a server snapshot.
