0. Plain language first

Upstream — the system data comes from: Odoo. Downstream — the system documents go to: PEAK. Draft — a document PEAK holds but has not approved; a person approves it inside PEAK. Read back — Debt asking PEAK what happened to a draft. Idempotency key — a unique tag stored before a create call so that a retry can never create the document twice. Gap list — orders Odoo says are installed but the sheet never marked Order-Done.

1. The picture in one line

Odoo → Debt → PEAK, and only drafts cross the last arrow. Odoo supplies orders, customers, installation dates and helpdesk tickets and is never written. Debt owns the case, the contact log, the promises, the next actions, the holds and the reviews — none of which reach a ledger (FigJam: 25 of 48 outcomes post nothing). PEAK receives every ledger-touching outcome as a draft in the instance company_id names (EPC for cash and service, SPV for lease; REQ-ENT-001 stands), and a person in PEAK approves it. Debt reads the approved state back and shows it on the case.

3. The Odoo leg — three new reads

Beside sale.order and res.partner (v1.1), Debt reads: the installation dates on the order or its project (planned, confirmed by EPC, actual), which drive the invoice pipeline's three-day look-ahead and the installation-day check; the helpdesk ticket model, so a service issue can carry its ticket and learn when it closes; and the order status, so the gap list "installed per dates, not Order-Done per status" is computed rather than discovered by a person. Field names are confirmed by discovery on first live contact (v1.1's discovery-first rule stands); the mapping lands in Odoo Integration v1.2 section 2.

4. The PEAK leg — draft only

The client keeps two verbs: create a draft and read a document's state. There is no approve, post, update or delete, and a test asserts it. Every outgoing document is a peak_document (Data Model v2.3) whose idempotency key is stored before the call. States: PENDING, DRAFT_CREATED, APPROVED_IN_PEAK, REJECTED, UNSENT. The 23-outcome table and the two-instance routing live in PEAK Integration v1.2. The QR code on a customer invoice is read from the approved document, so a link cannot be sent for a draft that AR has not yet approved — the pipeline shows "waiting for AR" until it is.

5. Slips, receipts and OD-02

A slip confirmed by an officer creates a draft receipt at invoice level in the instance the invoice belongs to; AR approves it in PEAK. Nothing changes for allocation: instalment components are not written while the allocation order (OD-02) is open, and a short payment still raises the exception the v2.1 webhook raised. A receipt that cannot be tied to one customer stays in the Finance exception queue (FigJam S07) and credits nothing.
